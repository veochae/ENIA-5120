🎯 1. Ruling Out Outliers

Last lecture we built the 3-standard-deviation rule of thumb: a value is flagged if it sits more than 3 SDs from the mean. In R, that's just arithmetic you already know how to write. mean() and sd() give you the two numbers, abs() gives you the distance regardless of direction, and filter() keeps only the rows that pass.

climate %>% filter(abs(temp_c - mu) <= 3 * sd_val)

That single line keeps every row whose temperature is within 3 SDs of the mean, and quietly drops the rest.

One pass isn't quite enough here. A couple of the fabricated readings in this dataset are so extreme (close to 1000°C) that they drag the standard deviation itself way up when you calculate it, which stretches the "acceptable" range out far enough to hide a third bad value (a −180°C reading) that would otherwise be an obvious outlier. This is a real, known limitation of the 3-SD rule: a handful of severe outliers can inflate the very spread measure used to catch them, effectively masking themselves and each other. The fix is a second pass using the physical bound from Lab 1, no surface reading is possible outside ±60°C, as a backstop after the statistical check. Two different tools, catching two different kinds of "wrong."
Why this runs before duplicates. One of the "duplicate" station-years from Lab 1 isn't really a duplicate at all, it's the same station and year logged twice, once with a real temperature reading and once with a fabricated one (one of the extreme readings you flagged as impossible last week). If you removed duplicates first, R would have no way of knowing which of the two rows to keep, and by default it keeps whichever one comes first in the file, which happens to be the broken one. Running the outlier check first means the fabricated reading is already gone by the time you get to duplicates, so there's nothing left to decide.

👯 2. Fixing Duplicate Station-Years

Remember from Lab 1: station_id alone repeats naturally, once per station per year, so checking it by itself isn't useful. A real duplicate means the same station_id and the same reading_date showing up twice.

duplicated() can check more than one column at once if you hand it a small table instead of a single column. It marks the first occurrence of each combination FALSE, and every repeat after that TRUE.

duplicated(climate[c("station_id", "reading_date")])
Analogy: think of it like checking guests into a hotel by first name and last name together, not first name alone. Plenty of guests share a first name, that's not a problem. Two guests sharing both a first and last name is the actual red flag.

Keep only the rows where that check comes back FALSE, and the repeats are gone.

🕳️ 3. Fixing Missing Values

You already know the decision: delete when it's a handful of rows, impute when deleting would cost too much data. For co2_ppm, you're imputing.

coalesce() is a simple idea with a slightly odd name: it looks at a column and, wherever it finds a missing value, replaces it with whatever backup value you give it. Everywhere the column already has a real value, coalesce() leaves it alone.

mutate(co2_ppm = coalesce(co2_ppm, mean_co2))
Analogy: coalesce() is like a form that says "if this field is blank, use this default instead." It never overwrites an answer that's already there.

Two columns have this problem: energy_source ("solar" vs. "Solar") and location (you'll recognize this one, it's the exact Arlington / ARLINGTON / arlington example from the Session 1 slides). str_to_lower() forces every value in a column to lowercase in one pass, so all three versions of Arlington collapse into one.

n_distinct() is your before-and-after check, it just counts how many different values exist in a column. Run it before the fix and after, and the drop tells you exactly how many fake categories you just merged away.

🏷️ 5. Factors: Nominal vs. Ordinal in R

Session 1 covered the idea: nominal categories have no order (Solar, Wind, Coal are just different labels), ordinal categories do (Low < Medium < High is a real ladder). Today's the first time you'll actually write the R code for it, using factor().

For a nominal column, factor() on its own is enough:

climate$energy_source <- factor(climate$energy_source)

For an ordinal column, you tell R the rungs of the ladder, in order, and mark it as ordered:

climate$climate_risk_level <- factor(
  climate$climate_risk_level,
  levels = c("Low", "Medium", "High"),
  ordered = TRUE
)
Here's the part that matters for this lab. R will only accept values that exactly match one of the levels you listed. Anything else, like the "TBD" and "Extreme" values you flagged in Lab 1, silently becomes NA. That's not a bug, it's the whole reason to do this: assigning an ordinal factor doubles as a built-in validity check. You didn't have to go hunting for the bad values again, R just told you.
Analogy: think of levels as a guest list at the door. If your name's not on it, you don't get in, you get turned into NA instead.

Once you see how few values are salvageable, you'll make a judgment call: is it worth recoding 3 bad values out of 146, or is the column better off dropped entirely? There's no single right answer here, that's the point.

🛠️ 6. Fixing Broken Types

6.1 sensor_active

This column should only ever hold TRUE or FALSE, but a few rows have "Yes" and "No" instead, which is why R stores the whole column as text instead of a clean logical column. The fix is two steps: first make every value read "True" or "False", then convert.

mutate(sensor_active = case_when(
  sensor_active == "Yes" ~ "True",
  sensor_active == "No"  ~ "False",
  TRUE ~ sensor_active
))

case_when() reads top to bottom: if the first condition matches, use that result; if not, check the next one; the final TRUE ~ line is a catch-all for "nothing else matched, leave it as is." Once every value is a clean "True"/"False" string, as.logical() converts the whole column in one call.

6.2 reading_date

Six rows have dates written out as text, like "Jan 15th, 2020", instead of the standard format the rest of the column uses. There are only 5 distinct bad strings in the whole dataset, so this doesn't need anything fancy, just a direct swap for each one.

Found in the dataCorrect value
Jan 15th, 20162016-01-15
Jan 15th, 20182018-01-15
Jan 15th, 20192019-01-15
Jan 15th, 20202020-01-15
Jan 15th, 20222022-01-15

Same case_when() pattern as above, five conditions instead of two. Once every value looks like "2020-01-15", as.Date() converts the column with no extra arguments needed, R recognizes that format automatically.

Why not just tell R "this means January 15th"? R can't guess "15th" means the number 15, "th" isn't part of any date it recognizes. Swapping the whole string is simpler and safer than trying to strip just the "th" out, since it also fixes the month-name and format at the same time, not just the ordinal suffix.

📉 7. Diagnosing and Fixing Skew

precipitation_mm has a long right tail, exactly the kind of shape lecture covered. But before transforming it, there's a catch this column has that temp_c didn't.

Check for negative values first. Rainfall can never be negative, that's impossible by definition, the same way a 500°C surface reading was impossible. But a negative value isn't necessarily far enough from the mean to trip the 3-SD rule, so it can slip through a purely statistical check. This is exactly the distinction from lecture: some bad values are statistically rare, others are logically impossible no matter how common they look. Filter these out with plain domain knowledge before you do anything else with this column, log() of a negative number isn't a real number in R, it'll break your plot.

Once that's handled, the transform itself is one line: log(precipitation_mm). Plot the raw column, plot the log-transformed version, and compare the shapes. You only need the log-transformed values for this one comparison, so compute them inline for the plot rather than saving a permanent `log_precip` column, no reason to carry a one-off diagnostic column through the rest of the dataset.

🎨 8. Visual Confirmation: ggplot2 Basics

Every ggplot2 chart is built the same three-part way, no matter what it ends up looking like:

  • The data you're handing it.
  • What goes on which axis, set inside aes() (short for "aesthetics").
  • What kind of chart you want, a geom_*() layer.
Analogy: think of it like ordering a sandwich. ggplot(data) is picking the bread, aes() is deciding what goes where in the sandwich, and geom_*() is choosing what the sandwich actually is, hot or cold, toasted or not. Same three steps, different filling every time.

You'll use three different geoms today:

FunctionWhat it shows
geom_histogram()The shape of a numeric column. What you'll use to check temp_c and precipitation_mm.
geom_col()A count per category. What you'll use to check energy_source.
geom_line()How a value changes over time, connected point to point in order.
Why geom_line() needed section 6 first. A line chart draws points in whatever order the data is sorted in. If reading_date were still stored as text, R would sort it alphabetically, "Jan 15th, 2020" would land near "Jan 15th, 2022" purely by coincidence of spelling, not chronology, and the line would zigzag nonsense. Because you already converted reading_date to a real Date in section 6, R now sorts it the way a calendar does, and the line actually tells a story.
